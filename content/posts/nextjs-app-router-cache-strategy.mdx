App Router에서는 화면 단위보다 데이터 성격에 맞춰 캐시 정책을 나누는 편이 유지보수에 유리합니다. 사용자별 데이터, 공개 목록, 즉시 반영이 필요한 액션을 구분해 팀 규칙으로 남기는 과정을 정리했습니다.

# 운영 기준 세우기

캐시 정책은 프레임워크 옵션을 고르는 일이 아니라, 서비스가 어떤 데이터를 언제 신뢰할지 정하는 운영 기준입니다.

## 캐시 전략 한눈에 보기

페이지 전체를 하나의 정책으로 묶기보다 데이터의 변경 주기와 사용자 의존성을 기준으로 나눕니다. 공개 목록은 재검증 주기를 두고, 개인화 데이터는 요청마다 새로 가져오도록 분리합니다.

> 캐시 정책은 빠르게 만들기 위한 설정이 아니라, 어떤 데이터가 언제 신뢰할 수 있는지 팀이 합의하는 약속입니다.

### 사용자 데이터 캐시

사용자 프로필, 알림, 권한처럼 로그인 상태에 따라 달라지는 값은 캐시를 최소화합니다. 서버 컴포넌트에서 읽더라도 사용자 컨텍스트가 섞이지 않도록 no-store 기준을 먼저 적용합니다.

### 데이터 신선도 조절

상품 목록이나 블로그 목록처럼 여러 사용자가 공유하는 데이터는 revalidate를 사용해 성능과 최신성을 함께 맞춥니다. 변경이 잦지 않은 데이터는 짧은 주기보다 명확한 갱신 이벤트를 두는 편이 안정적입니다.

#### 즉시 갱신이 필요한 경우

댓글 작성, 예약 변경, 결제 상태처럼 사용자가 바로 결과를 확인해야 하는 흐름은 서버 액션 이후 관련 경로를 재검증합니다. UI에는 낙관적 업데이트를 적용하되 실제 데이터와 다시 동기화합니다.

```ts
const cachePolicy = {
  user: "no-store",
  catalog: "revalidate",
};
```

### PR 템플릿 체크

PR 템플릿에는 데이터 종류, 캐시 정책, 재검증 방식, 실패 시 fallback을 체크하도록 둡니다. 리뷰어가 정책 누락을 빠르게 찾을 수 있어 배포 후 캐시 이슈를 줄일 수 있습니다.

## 팀 규칙으로 남기기

캐시 정책은 코드 스타일보다 운영 규칙에 가깝습니다. 팀이 자주 쓰는 데이터 유형별 기본값을 문서로 남기고 예외만 리뷰에서 논의하면 판단 비용이 낮아집니다.

## 마무리

캐시 전략은 한 번 정하고 끝나는 설정이 아니라, 제품의 데이터 흐름이 바뀔 때마다 다시 확인해야 하는 운영 규칙입니다.
