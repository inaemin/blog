## 숫자보다 기준

성능 예산은 숫자를 맞추는 체크리스트가 아니라, 제품 의사결정을 돕는 기준입니다. 어떤 화면에서 어떤 경험을 지켜야 하는지 먼저 정해야 합니다.

![성능 예산을 제품 기준으로 연결하는 흐름](/images/posts/performance-budget-flow.png "성능 예산을 제품 기준으로 연결하는 흐름")

> 좋은 성능 예산은 개발팀만 보는 숫자가 아니라, 제품팀이 우선순위를 고를 때 함께 보는 약속이어야 합니다.

### 지표를 경험 언어로 바꾸기

LCP, INP, CLS 같은 지표는 그대로 공유하면 맥락이 부족합니다. 핵심 화면에서 사용자가 기다리는 시간, 입력이 막히는 순간, 레이아웃이 밀리는 장면으로 번역해야 논의가 빨라집니다.

#### 홈 화면 예산

홈 화면은 첫 인상이 결정되는 구간이므로 이미지 우선순위와 초기 JavaScript 크기를 가장 엄격하게 봅니다. 대신 상세 페이지의 보조 인터랙션은 사용 시점에 로드해도 괜찮습니다.

```ts
const performanceBudget = {
  home: { lcp: 2500, jsKb: 170 },
  article: { lcp: 2800, jsKb: 140 },
};
```

## 리뷰 가능한 규칙

성능 규칙은 코드 리뷰에서 확인할 수 있어야 합니다. 이미지 우선순위, bundle 증가, 서버/클라이언트 경계처럼 반복해서 등장하는 항목을 문서화하면 팀의 판단 비용이 줄어듭니다.

### PR에서 바로 확인할 항목

PR 설명에는 성능에 영향을 주는 변경을 명시합니다. 이미지가 추가됐는지, 새 클라이언트 컴포넌트가 생겼는지, 번들 크기가 얼마나 늘었는지를 리뷰어가 한 번에 확인할 수 있어야 합니다.

![작은 성능 체크 메모](/images/posts/performance-review-note.png "작은 성능 체크 메모 | width=260")

## 운영 지표로 이어가기

예산은 배포 전에만 보는 기준이 아니라 운영 중에도 계속 비교해야 합니다. 실제 사용자 지표가 기준을 넘으면 제품 의사결정 회의에서 원인과 trade-off를 함께 다룹니다.
