## 서버 컴포넌트로 둘 것

데이터를 읽고 정적으로 보여주는 컴포넌트는 서버 컴포넌트로 유지합니다. 페이지, 글 목록, 글 본문, 푸터는 클라이언트 상태가 필요하지 않으므로 서버에서 렌더링하는 편이 자연스럽습니다.

![서버와 클라이언트 컴포넌트 경계를 나누는 흐름](/images/posts/rsc-boundary-flow.png "서버와 클라이언트 컴포넌트 경계를 나누는 흐름")

### 데이터 읽기 영역

목록, 상세 본문, 추천 영역처럼 데이터를 읽고 바로 보여주는 조각은 서버에 남깁니다. 클라이언트로 옮기기 전에 사용자 입력이나 브라우저 API가 정말 필요한지 먼저 확인합니다.

#### 캐시와 함께 판단하기

서버 컴포넌트는 캐시 정책과 같이 판단해야 합니다. 같은 서버 렌더링이라도 공개 데이터와 사용자별 데이터는 재검증 기준이 완전히 다릅니다.

## 클라이언트 컴포넌트로 분리할 것

사용자 입력, 클릭, 브라우저 API, effect가 필요한 영역만 클라이언트 컴포넌트로 분리합니다. 이 블로그에서는 모바일 메뉴, 댓글 작성 폼, Turnstile widget, 스크롤 기반 TOC가 대표적입니다.

> 클라이언트 컴포넌트는 나쁜 선택이 아니라, 상호작용이 필요한 경계를 작게 표현하는 도구입니다.

```tsx
export function CommentComposer() {
  const [comment, setComment] = useState("");

  return <textarea value={comment} onChange={(event) => setComment(event.target.value)} />;
}
```

### 상호작용 leaf만 분리하기

페이지 전체를 client로 올리면 데이터 fetching과 번들 크기를 동시에 잃기 쉽습니다. 버튼, 입력, 토글처럼 상호작용이 발생하는 leaf만 분리하면 서버 렌더링의 장점을 유지할 수 있습니다.

## 경계를 작게 유지하기

전체 페이지를 client로 만들지 않고, 상호작용이 필요한 가장 작은 leaf component에만 `use client`를 붙이는 것이 핵심입니다.

### 점검 체크리스트

컴포넌트를 나누기 전에는 데이터 소유권, 이벤트 필요 여부, hydration 비용을 같이 봅니다. 이 세 가지가 분명하면 서버와 클라이언트 경계를 리뷰하기 쉬워집니다.

![작은 RSC 경계 메모](/images/posts/rsc-boundary-note.png "작은 RSC 경계 메모 | width=260")

#### 리뷰에서 남길 질문

이 컴포넌트가 브라우저 API를 직접 쓰는지, 상태가 사용자 입력에서 시작되는지, 서버에서 먼저 계산할 수 있는지 질문으로 남기면 경계가 과하게 넓어지는 일을 줄일 수 있습니다.
